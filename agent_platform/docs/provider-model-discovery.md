# 服务商模型发现与动态接入

2026-11-05 新增。平台管理员可以在“模型目录 → 获取服务商模型”或“平台运营 → 平台模型部署”中添加服务商连接、获取模型列表并选择接入。模型标识来自服务商接口；后续增加模型不需要修改 `.env`、YAML 或源码中的模型名称。

## 使用流程

1. 添加服务商名称、HTTPS API 基础地址和 API Key，例如 `https://api.example.com/v1`。密钥加密保存且不回显。当前适配兼容 OpenAI 的 `GET /models` 接口；模型列表中可能包含多种用途的模型，接入时选择适合平台文本对话/Responses 调用的模型。
2. 保存后自动获取列表，也可点击“获取模型”重新查询服务商。页面展示最新模型名称、标识及服务商返回的基础信息，支持搜索。服务商连接保存于数据库；发现结果不是代码内置清单。
3. 选择模型，确认是否支持工具调用，然后点击“接入模型”。后台通过 LiteLLM 控制接口登记路由，路由保存于网关数据库；接入期间展示处理状态。重复选择同一连接的同一模型复用已有操作和部署。
4. 在组织模型目录中，具有平台报价权限的管理员可继续确认显示名称、别名、输入/输出价格、上下文和输出上限，并授权给当前组织。新模型默认别名带部署标识后缀，避免不同服务商的同名模型覆盖已有授权；可以在提交前修改别名。
5. 授权后自动请求组织网关同步。普通组织成员继续只看到已授权模型；不会因发现服务商模型而自动获得全部模型权限。若只登记平台部署，可后续在平台运营页面向组织授权。

模型列表通常不提供可靠的合同价格。界面不猜测价格，也不把新增模型设为免费；报价继续使用原有的精确金额、版本快照和平台权限流程。服务商未提供上下文或输出上限时，表单使用平台默认值供管理员确认。

## API

以下接口均要求当前有效的 `platform.models.manage` 权限，写接口沿用 Cookie 会话与 CSRF 检查。

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| `GET` | `/api/v2/platform/providers` | 读取平台服务商连接及最近一次发现结果，不包含密钥 |
| `POST` | `/api/v2/platform/providers` | 保存 `{name, api_base, api_key}`，返回连接元数据 |
| `POST` | `/api/v2/platform/providers/{id}/discover` | 请求重新获取模型，返回 HTTP 202 和操作标识 |
| `POST` | `/api/v2/platform/providers/{id}/imports` | 选择 `{model_id, tools}` 接入；必须来自该连接已发现的目录 |
| `GET` | `/api/v2/platform/provider-operations/{id}` | 查询获取/接入状态和结果 |

新增部署后，组织授权继续使用 `POST /api/v2/platform/tenants/{tenant}/models`，要求平台模型管理和报价权限；组织同步使用原有 `.../gateway/enroll`。现有模型目录、历史运行、价格快照和组织默认模型保持各自的业务含义。

## 后台和凭据边界

迁移 `0020_provider_catalog` 新增连接、密文和操作三张平台表。API 角色对密文表只有 INSERT 权限；gateway-sync 负责解密、从服务商获取列表及创建网关路由，Worker 与维护角色不能读取服务商密文。API 请求后轮询操作状态，网络 I/O 位于数据库事务之外，供应商访问与原有组织授权同步使用独立后台循环。

服务商查询限制为公网 HTTPS，拒绝凭据内嵌 URL、重定向、私网或混合 DNS 地址。连接固定校验后的 IP，保留原域名证书验证与 SNI，不读取代理环境配置；响应最多 2 MiB、目录最多 10000 项，失败只保存稳定错误码。平台模型管理权限在排队及实际处理时重新核验。

接入操作在发送网关写请求前保存发送标记，并使用稳定部署标识。网关写结果不确定时，只读取对应部署核查，最多处理三次，不盲目重发创建请求；缺少确认信息的模型不会登记为可授权部署。超过次数的未知状态保留给平台核查，不会显示为接入成功。过期后台持有者不能更新新持有者的任务。

## 原生流式能力与升级

接入的文本对话模型需要兼容 Responses 流式接口。创建路由时，`model_info` 明确登记 `mode: responses`、`litellm_provider: openai` 和 `supports_native_streaming: true`。当前锁定的 LiteLLM 1.83.0 对热加入模型按上游名称查找能力时存在缺口；Compose 与 Helm 均加载 `platform_native_streaming.proxy_handler_instance`，在请求分发前补齐显式声明的能力，支持新模型即时流式调用。原因、验证及后续移除兼容层的条件见[流式输出优化](streaming-performance.md#2026-11-05-动态接入模型整段出现的问题)。

升级前已经接入的 `provider-*` 路由需要补齐上述 `model_info` 字段。网关管理员应先通过 `GET /model/info` 核对平台部署 ID 和上游模型，再使用 `PATCH /model/{model_id}/update` 只更新这些能力字段，保留服务商连接与密钥。`POST /model/update` 是旧接口，不能用于此元数据修复。本机现有的 3 个服务商路由已完成修复。接口语义参考 [LiteLLM 模型管理](https://docs.litellm.ai/docs/proxy/model_management)。
